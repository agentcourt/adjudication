# Web UI Work Plan: 2026-07-11a

## Direction

The web console should use service event logs as the primary source for live progress.  The runtimes already record attorney actions, ADC actions, juror votes, evidence reads, failures, and phase changes in NDJSON artifacts, and the existing artifact proxy supports byte ranges.  Processing those logs through server-rendered pages gives operators live state without adding a partial transcript lifecycle or a push transport.

Incremental transcript generation should be deferred.  It would require runtime changes to rewrite `transcript.md` during active runs, define whether a transcript artifact is provisional or terminal, and protect existing assumptions about terminal artifacts.  The event logs already contain the filing and decision data needed for an operator view, so the transcript can remain an end-of-run artifact.

The console should keep its current shape: Spartan pages, service APIs only, minimal JavaScript, and raw service details available when useful.  The next work should reduce expensive page loads, make failures easier to inspect, and give operators useful case state without hiding the service records.  Changes should use the artifact and case APIs already exposed by ARB, AARD, and ADC.

## Candidate Work

| Priority | Candidate | Scope | Reason |
| --- | --- | --- | --- |
| 1 | Event tail page | Add `.../cases/{case_id}/events` backed by `Range` reads against `events.ndjson`, dropping any partial first line and rendering the last N complete events. | The current case page downloads the whole event log on each refresh and keeps eight rows, which is too expensive for large ADC runs. |
| 2 | Event detail page | Add a page keyed by event offset or line number that shows the full event, payload, response, and adjacent events. | Compact rows can stay compact while full filing text, ADC responses, and failure details remain available. |
| 3 | Event filters | Add server-rendered query filters for phase, actor, event type, failures, filings, evidence reads, and juror votes. | Operators need to find the relevant parts of long logs without downloading or reading the entire file. |
| 4 | Log viewer | Add a first-class viewer for `stdout_log` and `stderr_log` artifacts with head, tail, and byte-range controls. | Large service logs contain provider and runtime failures, but raw log downloads are cumbersome in the browser. |
| 5 | Unknown-case presentation | Render missing cases as an explicit service error page with no management actions and with the service response preserved. | The current empty record plus stale action links creates ambiguity for a routine operator error. |
| 6 | Case-list operational facts | Add compact facts to list rows: phase or resolution, start and finish times, failure count, and newest event type when available cheaply. | The list page should identify cases needing attention before the operator opens each case. |
| 7 | Artifact type handling | Render common artifacts by type: Markdown as readable text with a raw link, NDJSON with tail controls, JSON with bounded rendering, and logs through the log viewer. | The artifact list should remain the entry point, but common artifact formats need useful operator views. |
| 8 | Home service status | Show whether each backing service responds, which scopes exist, and any exposed service root or configuration facts. | This reduces confusion when the console is reachable but a backing service is down or misconfigured. |
| 9 | ARB evidence manifest uses | Add `uses` data to ARB evidence manifests, matching the ADC evidence-page behavior where possible. | The existing ARB evidence page has an empty Uses column because the service data lacks those labels. |
| 10 | Request-console history | Consider a browser-session or server-process-local history of recent method, path, and payload entries. | Manual testing repeats the same service requests, but this should stay low priority because it can drift into a separate API client. |

## Suggested Order

The first implementation should be the event tail page.  It addresses the largest operational cost observed in testing, uses the existing artifact proxy, and gives a place to render filings and decisions without changing runtime output.  The first version can show the last N events, preserve the existing ten-second refresh behavior for active cases, and link each row to an event detail page once offsets or line numbers are available.

The second implementation should be the log viewer.  Service logs already appear as links in case records and artifact tables, and they often contain the information needed to diagnose provider errors.  A range-based viewer would make those logs usable while preserving raw artifact routes for exact bytes.

The third implementation should clean up unknown-case handling.  This is a small correctness task with low design risk.  It should remove management links from missing-case pages and show the service error in a direct, bounded response panel.

The fourth implementation should add compact operational facts to the case lists.  The design should avoid expensive full artifact reads for every row unless the service already exposes the required facts.  If the facts require event-log reads, they should wait until the event-tail code has a reusable path for bounded artifact reads.

## Deferred Decisions

ARB evidence `uses` belongs to the runtime or service data model rather than the console.  The UI already renders `uses` when the manifest provides them, as ADC does.  This should be handled as a separate service-data task after the operator pages improve.

Request-console history should remain optional.  A small history would help manual testing, but persistent saved requests would add state to a console that currently proxies service APIs without keeping user workflow data.  If implemented, it should stay process-local or browser-session-local and avoid becoming a second API client.

Service push mechanisms should remain out of scope for this plan.  Server-sent events, chunked streaming, and WebSockets add connection management and state beyond the current server-rendered design.  The observed event rate fits periodic refresh and byte-range reads.
